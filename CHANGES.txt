SMART342 FOR WINDOWS - CHANGES
==============================

What is new in 0.5.0 (2026-10-18) - the first public test version
-------------------------------------------------------------------
* Fix streaks shows the right result. In a RAW, green is the CCD's own samples, but the scanner moves red and blue
  sideways by part of a photosite to line them up with green, so the program's prediction for red and blue was wrong:
  it showed about 0.5 - 0.6 % left when a RAW made with the stored vector had 0.08 % in all three colours (hardware,
  18 Oct). The result, the dust check and the dust repair now use green; a repair is applied to all three colours alike
  and limited to 3 %. 0.4.x could write red / blue errors of up to 11 % at the repaired places, and repaired only the
  first 16 of them: if you stored a vector with 0.4.x and the result window listed dust places, run Fix streaks again.
* Fix streaks names the selected holder plainly and asks for it to be the one in the scanner (the lens is chosen from
  the holder in the window), and for a frame with clean, unscratched glass.
* New RAW exposure "Long x2" and "Long x4" (experimental) for negatives and other dense film: one pass with 2 or 4 x the
  integration time, saved as it comes. A colour negative uses only about an eighth of the scanner's range at Normal
  exposure (hardware, 18 Oct: about 640 brightness levels in green); Long x4 gives about four times as many and less
  noise. The positive (POS16) is matched to it in density. Not yet tried on the scanner as a single pass (the same
  longer exposure has run many times as HDR's second pass).
* Stop during a streamed RAW says at once that the whole crop is one picture and is finished and saved first (up to
  about 2 minutes for a full 35 mm frame).
* Any SCSI card: at every start the program asks the card's driver how much data one command may carry (Windows'
  standard query - nothing is sent to the scanner), writes it to the log ("SCSI card limits") and warns if it is below
  the 300 KB the Scitex software needs, with how to raise it. The transfer buffer is now aligned to memory pages, so a
  300 KB read needs exactly 75 pages and meets every card's alignment rule. A command refused for being too large
  (Windows error 87) is explained as such, instead of "the scanner is not answering".
* User guide (README.txt) - a short basic part first, then the details and the tested hardware - MIT licence
  (LICENSE.txt) and NOTICE.txt about the Scitex software in the package.
* Hardware session 18 Oct (0.4.1): HDR +2 with step-and-hold on a full 35 mm frame - aligned in 9 bands, spill-over
  check 0.025 %, no green marks; Stop during a streamed RAW waited for the picture, the scanner kept working; negative
  with POS16; Fix streaks stored, RAW of the empty frame 0.08 % above noise (was about 1 %).


What was new in 0.4.1 - better HDR
----------------------------------
* HDR no longer lets light spill from overexposed areas into the shadows. In the longer pass the CCD's green row can
  spill charge from very bright areas (sky through leaves) into its neighbours; the merge took some of that as picture
  and left small bright green marks next to bright areas. Now the longer pass must agree with the normal pass within
  what the noise allows; where it is brighter than that, the normal pass is used (on the 13 Oct test slide: every mark
  gone, 0.09 % of the shadow pixels affected, the shadows as clean as before).
* HDR aligns the two passes more precisely: the shift between them is measured in bands along the scan and for each
  colour, not once for the whole picture. Two passes do not land exactly on the same lines - they drift by up to
  0.2 pixel over a 35 mm frame and red lies a little differently from green (measured on this scanner, with both kinds
  of carriage motion). Left over now: about 0.04 pixel instead of up to 0.2.
* HDR now uses step-and-hold too (at the lens's CCD resolution or finer, as other RAWs): the carriage stands still
  while each line is exposed, also for the longer exposure, so the HDR is as sharp along the scan as a normal RAW.
* The miner progress bar is now an easter egg: the normal progress bar, and now and then the miner.


What was new in 0.4.0 - negatives, a guided streak calibration, a safe Stop
---------------------------------------------------------------------------
* Colour negatives (and black-and-white): with Media "Negative" the preview is shown as a positive, and every RAW of a
  negative also gets a positive TIFF next to it ("... RAW16 POS16.tif", 16-bit, gamma 2.2) - about 95 % of the way,
  ready for an editor. The orange mask is taken out and blacks and whites come out neutral: each colour is mapped in
  density between its own thinnest and densest part of the frame (the holder and clear film left out), then to light
  with one tone curve. The levels come from the preview's whole frame, so a crop of a detail keeps the frame's colours.
  Tools > Negatives: the positive on / off, contrast (softer / normal / harder), "keep the shown preview's levels" for
  a whole roll (the same colours for every frame; "each frame its own" goes back), and rotation of the positive (90
  right, 180, 90 left). The RAW itself is never changed. Saved.
* Fix streaks is now a guided measurement that works for any scanner (Tools > "Fix streaks"): clean the KEEP CLEAN
  strip and the glass, put the holder in with the selected frame EMPTY, press Start. The program checks on the
  preview that the frame is empty, makes 5 small RAWs of it (about 4 minutes; not saved), and makes the lens's clean
  gain vector from their white measurements (256 lines each - the preview's 16-line ones are not used any more). Before
  anything is stored it shows how much fine streaking the pictures would keep with the new vector and with the one in
  use; dust that only the white measurement saw (on the KEEP CLEAN strip) is found and repaired from the pictures, and
  a vector that is not better is not offered. Then, as before, the scanner software ends (it parks the scanner) and
  the program starts again; only the settings on this PC change, nothing is written to the scanner. Set up this
  scanner no longer stores vectors.
* Stop while the scanner is sending a picture now waits until the picture is in (a few seconds for a preview, up to a
  few minutes for a large RAW), then stops. Stopping in the middle of a picture left the scanner unable to calibrate
  ("B01018 CCD timeout"; switching it off and on was needed). Stops during the calibrations stop at once, as before.
* Large RAWs are streamed in one request by default (much faster than blocks: 145 s instead of about 24 minutes for a
  full 35 mm frame at 2662 dpi). When the scanner's memory still holds a large RAW block, that RAW is made of blocks.
* A new progress bar - a miner digging for a diamond - drawn sharp at any Windows display scaling (0.4.1: now and then).


What was new in 0.3.1 - no more streaks along the scan
------------------------------------------------------
* Fine streaks along the scan, largest in bright areas, were in every scan (about 1 %, single columns up to 5 %). Cause:
  before each scan the scanner software corrects every CCD pixel with a stored "clean gain vector" of the lens, and
  the ones in the settings file came from another scanner. Tools > "Fix streaks" stores THIS scanner's own, made from
  the white lines it measures before every preview and scan (0.4.0: a guided measurement with an empty frame, see
  above). Only the settings on this PC change, nothing is written to the scanner; the scanner software ends as at
  Quit (it parks the scanner) and the program starts again. The previous settings files are kept in the Logs folder.
  The log shows for every calibration how much would be left in the scans ("left in the scans after ... correction":
  about 1 % before, a few hundredths of a percent after).


What was new in 0.3.0 - for any Smart 342L, not only the one it was developed on
-------------------------------------------------------------------------------
* The scanner is found on any SCSI ID: first in Windows' own list of SCSI devices (nothing is sent to them), then by
  asking every ID. With several Scitex scanners you choose one; with none the program shows what it found and lets you
  type the ID (it is on the scanner's front panel). The place is saved; Tools > "SCSI connection" searches again.
* Your scanner's own parameters: the package now has the original Scitex settings file. At the first start the
  scanner software stops because that file belongs to another scanner (number 96250969); the program then offers to
  copy YOUR scanner's parameters from its flash disk into the settings - the same read-only copy as "Scanner(Flash
  Disk) --> Mac" in the original Calibration program - and starts again. Nothing is written to the scanner. The
  previous settings are kept as Smart342.Old, the parameter file read from the scanner is saved in the Logs folder.
* Set up this scanner (offered at the first start; Tools > "Set up this scanner" at any time): for each lens you have
  a holder for, choose the holder, put a piece of film with fine detail in it, and the program measures how far a lens
  step moves the picture (10 RAWs of a small area it picks itself, about 7 minutes per lens). Pixel shift uses it.
  Optional, if you have the Scitex focus chart: the lens's sharpness is measured too, and RAW sharpening (the SHARP
  file) uses it. The results are saved in smart342.ini under the scanner's number.
* Pixel shift predicts each next lens step better (a fit of all passes so far, held toward the measured step size,
  with the slow drift between passes) - checked on all recorded pixel-shift runs.
* RAW sharpening no longer sharpens along the scan for carriage motion blur when step-and-hold (on by default) has
  already removed it.


What was new in 0.2.0
---------------------
* A progress bar for every job, with "pass 2 of 3" and the time left - also for pixel shift, HDR, averaging, blocks,
  multi-frame previews and scan lists. It learns from the scanner's own progress reports and from the passes already
  made; until it knows enough it says "estimating the time".
* RAW gamma (new setting under RAW exposure): "Linear (as scanned)" as before, or "Gamma 2.2" - the same RAW written
  with a gamma of 2.2 (value = 65535 x (linear / 65535)^(1/2.2)), easier to view and edit. All measuring, averaging,
  merging and sharpening is done on the linear values first. The file's description says which was used. Saved.
* Step-and-hold is now a normal setting, on by default: Tools > "RAW step-and-hold". At the lens's CCD resolution or
  finer (2662 dpi with the 35 mm lens, 1349 dpi with the 6x6 lens, and always with pixel shift) the carriage stands
  still while each line is exposed - sharper along the scan, about 1.4 x the time. At coarser resolutions it is not
  used (it would not help there).
* Pixel shift uses the slow (constant-rate) lens moves by default - they avoid the carriage slips seen with fast moves.
* A quieter window: the log shows the program's own messages only. Everything else (the scanner software's own
  messages, the safety interlock, measurements) still goes to the log file. Tools > "Detailed log in the window" shows
  all of it.
* No more message about a "Scratch Folder" at the first start - it is answered by the program.
* Scanner switched off or disconnected while the program runs: a clear message instead of a crash, and closing the
  window works.
* Tools menu tidied: the everyday RAW settings first, tests and research items under Tools > Diagnostics.
* Help > About shows the version.

New in 0.1.23: pixel shift refined, colour registration for colour film
------------------------------------------------------------------------
* Your full-frame pixel-shift RAW of 10 Oct (35 mm lens, streamed, 3 x 3729 x 4997 pixels) worked: every pass
  complete, the scanner never had to wait. But one lens step moved the picture almost exactly one whole pixel
  (-0.99), so pass 2 sampled the same places as pass 1, and the next step had to be guessed from that.
* APPROACH FROM ABOVE: the lens carriage's steps are uneven (your lens test of 9 Oct, 6x6 lens: the first step 0.44
  pixel, the next ones about 1.15, and back at 0 the picture was 0.46 pixel off; 35 mm lens, 9 / 10 Oct: the first
  step 0.71, 0.89 and 0.99 pixel). Checked in the scanner software's own code and in all your sessions: it always brings the carriage to
  the lens position with a move UP - when the carriage is above it, it first goes 1 mm (157 steps) below, its own
  backlash correction - so the play was already taken up the same way; what differed was the last move: a long move
  for pass 1, a short move of a few steps for the others. Now every pixel-shift pass - the first one too - goes 8 steps above its step and then down to it; the
  scanner software then makes its own correction (1 mm below, then up), so EVERY pass ends with the same long move
  up into its position, exactly as the software reaches the lens position itself. The carriage stays within the
  range the software uses itself (never more than 32 steps above the lens position). Two or three motor moves more per pass.
  Whether this makes the positions more repeatable on your scanner is what the new lens shift test measures (below);
  if it says "straight" is better, add the line pixel_shift_approach=0 under [window] in smart342.ini.
* PIXEL SHIFT STEPS are now chosen by the expected error of the result: after each pass the program predicts, from
  the offsets measured so far, where each possible next step would put the samples, and takes the step that leaves
  the finer columns closest to a sample (a step may also repeat an earlier one). Steps far beyond the measured ones are
  not taken on a guess: their place cannot be predicted (the steps are uneven), so a near step that is as likely to
  help is preferred. The normal setting stops when the samples of every finer column lie on average within 0.1 of
  it (3 to 5 passes; before, "covered" within 0.35 was enough - on your 10 Oct frame that left half of the columns
  0.21 off).
* PIXEL SHIFT PASSES (Tools > Pixel shift passes; saved): "Up to 5" (normal, above) or "8" (all eight: the extra
  passes put more samples near each finer column, which are averaged - less noise; 8 x one RAW's time, about 27
  minutes for a full 35 mm frame). Only the passes nearest to each finer column are placed (a sample 0.1 column off,
  put on the column, costs more than it gains). Tested on the step sizes measured on your scanner (a synthetic
  picture, noise 80): 35 mm lens, 9 Oct: 8 passes error 53 against 83 normal; 10 Oct: 75 against 83; 6x6 lens: 51
  against 76. Simulator end to end: 8 passes 44 against 80 for 3 passes.
* LENS SHIFT TEST (Tools) now makes two series of six RAWs on a small crop - 0, +1, +2, +3, 0, +2 steps, first
  straight to each step as before, then from above - and reports the step sizes, how even they are and how well the
  positions repeat each way (about 6 minutes).
* COLOUR REGISTRATION on colour film: 0.1.22 needed every part of the picture to match between the colours; on your
  C-41 frame it found "no detail" and did nothing. Now each direction is judged on its own: it is corrected when most
  parts of the picture agree (checked on your C-41 pixel-shift RAW of 9 Oct: along corrected, red -0.68 and blue
  -0.20 line, afterwards within 0.08 line in 3 of 4 tiles; across the colours' pictures disagree, so across is
  left as delivered). On the black-and-white chart (s18 / s19) both directions are corrected as before.
* Your scanner stopping at "Quit" on 10 Oct: it had been switched off before the program was closed - not a fault.

  - Not known yet: how far your passes are apart and how much they differ - the first real run will show it.

  itself before every prescan (in the simulator 1.3 then 1.4) and then calibrates dark and white at that time, so
  a longer exposure would be calibrated away; the integration time also sets the CCD cycle time and the image
  processor's line timing. A longer exposure only for the picture data is possible in principle but needs more
  study and a careful first test on the scanner. Details in the project notes.

New in 0.1.11
-------------
* Gang masks (several frames in one cassette, e.g. 4 T35mm H, 3 T 6x7 H): Preview now previews every frame of the
  chosen cassette, one after the other, as the Mac program's Preview button does. The "Frame" box above the
  preview picks the frame that is shown, cropped and scanned ("of 4 (this cassette holds 4 frames)"). The scan
  list remembers the frame of each entry, so one list can take crops from several frames. Found in the original:
  its Preview button runs Handle_Preview_Button for frames 1 .. number of frames; opening a frame's thumbnail
  calls start_preview(frame); the scan request carries the frame number. Checked in the simulator: 4 previews,
  the scanner carriage goes to a different place for each frame, a scan of frame 3 is made at frame 3.
  "Automatic" (the original recognises the masks itself) cannot be tried in the simulator; the window asks the
  original after the first preview how many frames it found and waits for them - please try it once.

* RAW 16-bit TIFF (new file format choice): the scanner's own 12-bit data of the crop at the scan resolution,
  without gradation, colour table, sharpening or the 8-bit step - for any original and cassette (35 mm, 120,
  4 x 5, 8 x 10, gang masks).
  How it works: the original has a "Max Detail" function (User Guide 7.6): a prescan of a small area at the final
  resolution, kept as 12-bit data (the preview path, before any image processing). The window asks for a Max
  Detail of exactly your crop at your resolution and scale, and writes it as an uncompressed 16-bit RGB TIFF:
    - "<date-time> <file name> RAW16.tif" in Scans, tagged with the resolution, same pixel size as a normal scan
      of the same crop (checked: 2000 dpi on 24 x 36 mm = 1890 x 2835 in both).
    - Values: your scanner works in its 14-bit mode (the driver checks use_Inpol_14_bit), and the driver squeezes
      14 bits into 12 with a fixed table (unchanged up to 255, above that 1/4.2 per step - read from the driver,
      not assumed). The window undoes that table (each value goes to the middle of its 14-bit step) and writes
      14-bit x 4, so 16383 -> 65532. If a scanner does not use the 14-bit mode, the 12-bit value x 16 is written.
      The log says which. Linear data as the scanner measured it: it looks dark and flat until you set levels or
      a curve. Negatives are not inverted. Always RGB, also with Mode = Greyscale (the scanner's prescan is RGB).
    - Orientation: for transparencies the data is mirrored left-right, like the preview display and your real
      normal scans (checked on your 19:46 and 20:23 scans: the final scan is the mirror of the preview data).
      The Mirror tick mirrors it once more. Reflective originals: not mirrored (not checked on the scanner yet).
    - The allowed resolution range is the normal scan's (the same check in the original refuses the same crops).
    - A preview of the frame is needed first.
  Needed for this: the driver's prescan has a counter that only counts to 32767 samples per piece of data, which
  the original's own small Max Detail areas never reach. Larger areas made the driver loop for ever (found in the
  simulator). 0.1.11 widens that counter in memory when the driver is loaded (6 instructions, each checked to be
  exactly the expected one first, nothing written to disk or scanner; if the driver is different, RAW is switched
  off and the log says so). Checked in the simulator up to 4488 x 5787 pixels (8 x 10 at 600 dpi, 156 MB).
  Not known yet (please test): speed and memory on the real scanner for large areas, and whether the RAW area
  lines up exactly with a normal scan of the same crop.
* Scan list entries keep their own file format, so a list can mix RAW and normal scans.

What this is
------------
The original Scitex Smart342(L) 2.2.0 software (the main program and the ScannerDriver, the same files
that run in SheepShaver) running directly on Windows 10/11 x64. A built-in PowerPC emulator executes the
original program code unchanged; the scanner is reached through the Adaptec card with Windows' own SCSI
pass-through (the same call the relay used). No SheepShaver, VMware or relay is needed.

The window replaces the Mac screens with a simple panel that drives the original program through its
own built-in scripting interface: Original, Cassette, Mode, Media, Preview, resolution, format, crop and
Scan. Everything the scanner does - start-up, light measurement, prescan, final scan, the output file -
is done by the original Scitex code.

SAFETY
------
* A safety interlock is always on. It sits between the original driver and the scanner and holds back
  every command that would change what the scanner stores:
    - writes to the motion board's NV-RAM (parameters, scanner number, motor constants, lamp timer,
      status byte, light level),
    - loading new firmware into the motion board,
    - any flash-disk operation other than reading (so no Mac -> Scanner parameter copy can happen),
    - any SCSI command the driver does not use in normal operation.
  A held-back command is answered "done" so the program carries on; the log says
  "SAFETY INTERLOCK: held back ...". The original driver checks the NV-RAM at every start-up and wants to
  rewrite it whenever the checksum of the Mac-side parameters differs from the scanner's (that is what
  happened on 23.09 with the donor prefs). With the interlock it can only report the difference
  ("Laoding to NV_ram failed" in the log) - the scanner keeps its own parameters.
* No calibration and no Service functions exist in this program.
* The program must run as Administrator (Windows asks when you start it), like the relay did.
* Windows may say the program is from an unknown publisher (it is not signed): More info -> Run anyway.

How to use
----------
1. Unpack the whole folder somewhere, e.g.  C:\Users\SE\Desktop\Private\Scanners\Scitex Smart 342L\Smart342 for Windows
   Keep the folder structure: smart342.exe, Volume\, Simulator\.
2. Switch the scanner on and wait for the steady green light.
3. Start smart342.exe (answer Yes to the Administrator question).
   It finds the scanner on the Adaptec card by itself (it looks for SCITEX on SCSI ID 4).
4. Wait for "Ready." at the bottom. The start-up takes about as long as on the Mac.
   If the original program shows a message, it appears as a small window with its own buttons - answer
   it as you would on the Mac.
5. Choose Original / Cassette / Mode / Media and press Preview. The preview appears on the right.
6. Set resolution (dpi) - the allowed range for the cassette and crop is shown under it -, file format and
   file name. Drag a rectangle on the preview around the part you want
   (or tick "Crop (mm)" and type width, height and the left/top offset); without the tick the program's own
   default crop is used.
   Sharpness and Colour table: leave them, or pick one of the original's tables (with Negative: also the film
   type next to Media).
7. Press Scan. (Several crops: "Add crop to list" for each, then "Scan list".) The finished file is moved to the Scans folder (date and time are put in front of the name).
8. Close the window when done: the original program saves its settings and parks the scanner
   (this takes a few seconds).

Logs (please send these after the first test)
---------------------------------------------
Every start makes a folder in Logs\ named with the date and time. It contains
  trace.txt       - everything the original programs did (text)
  scsi-trace.bin  - every SCSI command and its data (same format as smart342-tracerelay)
  ui-log.txt      - what the window showed
Zip the folder and send it. It is what lets me compare the real scanner with the simulator.

Try it without the scanner
--------------------------
  smart342.exe --simulate
runs everything against a simulated scanner (a test pattern instead of a picture). It works on its own
copy of the volume (Volume-simulator), so it never touches the real settings. The simulated scanner uses
Simulator\flash14.bin (this scanner's parameter file) and Simulator\profile.txt (answers the real scanner gave).

Folder contents
---------------
  smart342.exe          the program
  Volume\               the Mac disk contents the original programs see (programs, prefs, tables)
  Simulator\            parameter file and answers used by the simulated scanner only
  Scans\                finished scans (created on first scan)
  Logs\                 one folder per start
